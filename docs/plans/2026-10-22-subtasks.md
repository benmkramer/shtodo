## Recommendation

Store the link. A subtask is an ordinary task with a new optional
`parent_id` field on its record. Nesting is one level: a parent is a
top-level task, and a subtask cannot have subtasks. Keep the task vector in
tree order, so each top-level task is followed directly by its subtasks.
Then one pass in canonical order validates the tree, prints it, and moves
it. No index, `HashMap`, or cached tree is needed anywhere. This order makes
cycles, self-parenting, deeper nesting, and dangling parents impossible to
store: validation rejects each one, every mutation checks before it applies,
and IDs are never reused because nothing is ever purged.

Write the lowest schema version that can hold the list. A list with no
subtask is saved as schema 1, in exactly today's layout, because the field is
omitted for top-level tasks. A list with at least one subtask is saved as
schema 2. New binaries read both. Released and unreleased older binaries
(beta.1 to beta.4, the tags build, and the due-dates build) keep reading every
list that has no subtask. They refuse a list that has one, with
`unsupported schema version 2`, and they never write its `tasks.json`. This
was measured with the installed beta.4 and a `74747a0` release build (see
[Compatibility probe](#compatibility-probe)). No
migration step runs, and data is never silently lost in either direction.
This relaxes the guarantee from the two earlier plans. "Old and new binaries
share every file both ways" becomes "both ways until a list gets its first
subtask". The owner accepts that in question 1. The relaxation applies per
list: the global list and each directory list are separate files.

A derived text token such as `parent:3` was considered and rejected. todo.txt
has no subtask convention. The token would show up in the row and the editor,
older binaries and plain text edits could break it, and every reader would
need an index to rebuild the tree (see Alternatives).

Deleting a parent moves it to trash with its live subtasks, all under one
deletion sequence. Restoring the parent brings exactly those subtasks back,
in place. Completion never cascades. The shell gains
`add --parent <ID>`, `parent <ID> <PARENT_ID|none>`, and the `list` filters
`--roots` and `--parent <ID>`. Text listing indents a subtask under its
printed parent, and stays byte-identical for lists without subtasks. JSON
task objects gain the reserved, always-present `parent_id` (a number or
`null`), and `schema_version` stays `1`. The JSON tasks come in tree order, so
an agent can rebuild the tree in one pass. In the TUI, subtasks are indented
and parents show a `2/5` progress count. A parent that does not match the
current view, search, or filter still appears, dimmed, above a subtask that
does. `A` adds a subtask, `>` nests the selected task under the task above,
and `<` promotes a subtask. All three defaults yield to existing bindings.
To make room for them at 80x24, the Help popup also covers the header row and
drops its bottom border, and `>` and `<` share one Help row. Collapse and
expand are deferred.

Ship it as two PRs, like the earlier plans. PR 1 (storage, shell, and JSON)
is useful to agents on its own. Its TUI already treats moves and deletions
group-aware, but draws rows flat. PR 2 adds the TUI nesting, keys, and Trash
grouping.

## Alternatives

### Storing the parent link

| Approach | Benefits | Costs and failure modes | Decision |
| --- | --- | --- | --- |
| Derived text token such as `parent:3` (todo.txt has no subtask key, so the key would be shtodo's own) | No schema change. Every binary reads every file both ways | The token is visible in rows, the editor, search, and JSON `text`, and an agent that rewrites text without it silently promotes the task. Older binaries and plain edits can write self-links, links to unknown IDs, deeper links, and cycles, so every reader must repair the tree with a rule such as "treat as top-level". Old binaries reorder and add without grouping, so every `list` and refresh must build an ID index. Reparenting becomes a text edit, with text conflict guards. Scope-local IDs inside text break when text moves between lists | Reject |
| Stored `parent_id`, schema stays 1, field omitted for top-level tasks | Lists without subtasks stay byte-identical | A file that says schema 1 but that schema 1 readers cannot read. Older binaries fail with a parse error that names a field instead of a version | Reject |
| Stored `parent_id`, lowest-version write: schema 1 without subtasks, schema 2 with | Lists without subtasks stay byte-identical and readable by every release. Lists with subtasks fail closed in older binaries with a clear version message. One source of truth. Structural validation under the lock | The no-migration guarantee is relaxed per list (question 1). Returning a list to schema 1 means removing every parent link, including those on deleted subtasks | Recommend |
| Stored `parent_id`, always schema 2 after the first write by a new binary | Simplest stamping | Every list a new binary touches becomes unreadable to beta.4, even without subtasks | Reject |
| Sidecar file of links beside `tasks.json` | Older binaries still read `tasks.json` | Two files cannot be replaced atomically or covered by one refresh token. Older binaries reorder and delete without updating the sidecar, which leaves dangling or misplaced links | Reject |

### Nesting depth

| Option | Benefits | Costs | Decision |
| --- | --- | --- | --- |
| One level | Cycles are impossible, and validation needs only the current top-level task. Indentation costs two columns at 40. Moves are "group" or "within group". `>`/`<` have one meaning | No sub-subtasks | Recommend (question 2) |
| Arbitrary depth with a limit, such as 3 | Outliner-style use | A stack of open ancestors in every pass. Indentation eats a 40-column row. `>`/`<` and `J`/`K` need level rules. Context rows become ancestor chains | Not now |
| Unlimited | None for a small list | All of the above, and no bound on row width | Reject |

The cost of going deeper later is bounded. `parent_id` already supports any
depth, and so does the JSON contract: agents rebuild trees from `parent_id`
and tree order, and the skill tells them not to assume depth 1.
`validate_tree` becomes a stack walk, still one pass in the same pre-order.
A list that uses depth 2 would be written as schema 3 under the same
lowest-version rule. One-level binaries would then refuse it, rather than
misread a link they cannot draw. The TUI would need per-depth indentation and
level rules for `J`/`K`, `>`, and `<`.

### Deleting a parent

| Option | Benefits | Costs | Decision |
| --- | --- | --- | --- |
| Cascade: the parent and its live subtasks share one new deletion sequence | Every hidden task is a real tombstone, so `deleted` stays truthful, `visible_tasks` is unchanged, and Trash can list them. Restoring the parent restores exactly the subtasks deleted with it. `u` restores the latest group | `restore` and `restore_latest` clear a group instead of one task. The uniqueness rule for sequences allows shared values on subtasks | Recommend (question 3) |
| Delete only the parent; its live subtasks are hidden while it is in trash | O(1) delete | A third state ("live but hidden"): `deleted: false` tasks that `list` omits. Every reader checks the parent's tombstone. Trash cannot show them | Reject |
| Refuse while the parent has live subtasks | No new semantics | One delete per subtask before the parent | Reject |
| Promote the subtasks to top-level on delete | Simple storage | Restructures silently, and restore cannot put the group back | Reject |

## Contracts

Terms: a **top-level task** has no parent. A **subtask** has a `parent_id`,
which names a top-level task. A **group** is a top-level task followed by its
subtasks, deleted ones included.

### Data model and invariants

`task::Task` gains one field, omitted on disk when `None`. The scratch check
below was compiled and run against `serde` and `serde_json` from the
lockfile's registry cache:

```rust
#[derive(Clone, Debug, Deserialize, Eq, PartialEq, Serialize)]
#[serde(deny_unknown_fields)]
pub struct Task {
    id: TaskId,
    text: String,
    completed: bool,
    deletion_sequence: Option<u64>,
    /// Absent on disk for a root, so a list without subtasks keeps its schema 1 bytes.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    parent_id: Option<TaskId>,
}
```

`deny_unknown_fields` stays on both structs. `Task::parent_id()` is the
accessor. Subtasks get ordinary IDs from `next_task_id`.

`TaskList::validate` enforces these invariants in its existing single pass,
on every load and before every save:

1. **One level.** A subtask's parent is a top-level task. No task is its own
   parent.
2. **Tree order.** A subtask comes directly after its parent's group has
   started, before the next top-level task. So canonical order is the tree
   in pre-order, and a parent always comes before its subtasks.
3. **Live parent.** A live subtask's parent is live.
4. **Deletion sequences.** Sequences stay unique, except that a subtask
   deleted with its parent shares the parent's sequence. A deleted subtask
   under a deleted parent has a sequence no higher than the parent's: it was
   deleted with it, or before it.
5. **Version.** `schema_version` is 1 or 2. A schema 1 list has no
   `parent_id`. A schema 2 list may have none: it is read as it is, and the
   next real save writes schema 1. Storage writes `required_schema_version`.

Invariants 1 and 2 make cycles, self-parenting, deeper nesting, and parents
that are missing or come later unrepresentable: the check compares each
subtask's `parent_id` with the one top-level task the pass is currently in.
A dangling parent cannot appear later either. IDs are never reused, and no
command removes a task record. Invariant 4 means `u` never meets a subtask
whose parent is still in trash, because the parent always holds the higher
sequence.

```rust
/// Lists with no subtask keep schema 1, which every released binary reads.
pub const SCHEMA_VERSION: u64 = 1;
/// Written only while some task has a parent; older binaries refuse it unread.
pub const SUBTASK_SCHEMA_VERSION: u64 = 2;

/// The lowest schema that can hold these tasks; storage writes exactly this.
pub fn required_schema_version(tasks: &[Task]) -> u64 {
    if tasks.iter().any(|task| task.parent_id.is_some()) {
        SUBTASK_SCHEMA_VERSION
    } else {
        SCHEMA_VERSION
    }
}

/// One pass in canonical order. Each subtask follows its parent's root row, so a parent that
/// is missing, later, nested, or the task itself cannot pass, and no index is built.
pub fn validate_tree(tasks: &[Task]) -> Result<(), ListError> {
    let invalid = |message: &str| Err(ListError::InvalidData(message.into()));
    let mut root: Option<&Task> = None;
    for task in tasks {
        let Some(parent) = task.parent_id else {
            root = Some(task);
            continue;
        };
        let Some(root) = root.filter(|root| root.id == parent) else {
            return invalid("a subtask must directly follow its parent's group");
        };
        match (root.deletion_sequence, task.deletion_sequence) {
            (Some(_), None) => return invalid("a live subtask's parent must be live"),
            // Deleted with the parent (equal), or before it (lower).
            (Some(parent), Some(child)) if child > parent => {
                return invalid("a subtask cannot be deleted after its parent");
            }
            _ => {}
        }
    }
    Ok(())
}
```

In `src/task.rs`, `validate_tree`'s state moves into the existing loop. The
uniqueness check skips the `HashSet` insert for a subtask whose sequence
equals its parent's.

### Storage and compatibility

- **Reading rule.** `parse_snapshot` accepts `schema_version` 1 or 2 and
  rejects every other value before the full parse, as today. Then
  `validate`, which today rejects any version but `SCHEMA_VERSION`
  (`src/task.rs:323-326`), accepts 1 and 2 and rejects a schema 1 list that
  has a `parent_id` (invariant 5). `parse_snapshot` does not stamp, so
  `validate` sees the version on disk. A schema 2 file with no
  `parent_id` at all, from a hand edit or a later binary, is accepted. It
  keeps schema 2 in memory, read-only commands and no-op mutations never
  rewrite it, and the next real save stamps schema 1.
- **Writing rule.** `Store::mutate_with_hook` calls
  `TaskList::stamp_schema_version()` after `apply` and before `validate`.
  It sets `schema_version` to `required_schema_version`. The test-only
  `save` does the same. Promoting the last subtask makes the next save
  schema 1 again. A write of an unchanged list never happens, because no-op
  mutations do not save.
- **Bytes.** For a list without subtasks, the field set, field order, pretty
  printing, and trailing newline are unchanged. Saving such a list produces
  the same bytes the current code would.
- **No migration.** Schema 1 files are read as they are. Nothing is
  rewritten until a normal mutation saves, and that save is schema 1 unless
  the list has a subtask.

The compatibility guarantee:

| Reader or writer | List without subtasks | List with a subtask (schema 2) |
| --- | --- | --- |
| This release and later | Reads and writes schema 1 | Reads and writes schema 2 |
| beta.1 to beta.4, the tags build, the due-dates build (shell; beta.4 and `74747a0` measured, beta.1 to beta.3 read from source) | Unchanged | Exit 1, `unsupported schema version 2 in <path>` (`command_failed` in JSON builds); `tasks.json` never written. A mutating command may create or touch `tasks.lock` first |

What the owner accepts in question 1: the promise from the tags and due-dates
plans that "beta.4 and new binaries share snapshots both ways" now holds only
until a list gets its first subtask. From then on, that list needs this
release or newer until every parent link is gone. Nothing is migrated in
place, and no binary in either direction can write over data it does not
understand. To make a list readable by older binaries again, restore any
deleted group that has subtasks, promote every subtask with
`parent <ID> none`, and delete again what should stay deleted. No downgrade
command is added. Agents on an older binary get `command_failed` with
`unsupported schema version 2`; the skill tells them to ask the user to
upgrade and never to edit `tasks.json`.

### IDs and lifecycle

| Event | Effect |
| --- | --- |
| Add a subtask (`add --parent P`, TUI `A`) | New ordinary ID; inserted at the end of P's group; P must exist, be live, and be top-level |
| Complete or reopen a parent | Only the parent changes. Subtasks keep their states |
| Complete the last open subtask | The parent does not change |
| Edit a parent or subtask | Text only; the link is unchanged |
| Delete a top-level task | It and every live subtask in its group get one new deletion sequence. Subtasks deleted earlier keep their own lower sequences |
| Delete a subtask whose parent is live | Its own new sequence, as today |
| Delete a subtask whose parent is in trash | It is already a tombstone: `Already deleted`, `changed: false` |
| Restore a top-level task (`restore`, Trash `r`) | Clears the tombstone on it and on every subtask that shares its sequence, in place. Subtasks deleted earlier stay in trash |
| Restore latest (`u`) | Clears every task with the highest sequence: one task, or a parent with the subtasks deleted with it |
| Restore a subtask whose parent is live | Restored in place in the group |

### Order and moves

Canonical order is tree order (invariant 2), so new subtasks are inserted
rather than pushed, and moves work on groups:

- `J`/`K` (`Mutation::MoveAdjacent`) move a task among its siblings only.
  For a top-level task, the siblings are the displayed top-level tasks. For a
  subtask, they are the displayed subtasks of the same parent. A top-level
  move exchanges the two groups with `swap_blocks`. Everything between them,
  including deleted groups, stays in place, as `swap_visible` keeps hidden
  slots today. A subtask move is today's `swap_visible` inside its group. At
  the first or last sibling, `neighbor` is `None` and nothing changes, as
  today. A subtask never leaves its group through `J`/`K`.
- The `MoveAdjacent` struct is unchanged. `projection::adjacent` becomes
  sibling-aware and is rechecked under the lock as today. A concurrent
  reparent of either task makes the neighbor stop being a sibling, which
  produces `ConflictKind::OrderChanged`.
- **One displayed-set predicate (PR 2, Stage 3a).** Context rows make a
  top-level task displayed when it does not match, so `matches` alone no
  longer describes the rows the user saw. The general form is
  `projection::displays_with(list, index, matches: impl Fn(&Task) -> bool)`,
  beside `matches_with`: true when the task at canonical `index` satisfies
  `matches`, or when it is a top-level task and some live subtask in its
  block does. It scans only that block, and only for a non-matching
  top-level task. `Projection::displays(list, index)` is the instance with
  the accepted filter (`Projection::matches`). The `MoveAdjacent` precheck
  only has the `&Task` from `list.task(*id)` (`src/mutation.rs:170`), so it
  looks up the canonical index instead, with a new
  `TaskList::position(id) -> Option<usize>` that is the same linear scan
  `task` does today, and then tests
  `!projection.displays(list, index)` in place of `!projection.matches(task)`
  (`src/mutation.rs:177-186`). `adjacent` picks top-level siblings with
  `displays` and subtask siblings with `matches`. The TUI row pass in Filter
  mode uses the preview predicate (`App::matches` wraps `matches_with` with
  `session.preview`, `src/app.rs:593-599`), so it calls `displays_with` with
  `App::matches` and draws the same context rows during the preview. The
  guard never sees the preview predicate: Filter mode resolves to Insert
  bindings (`Keymap::bindings_for`, `src/input.rs:907-916`), so no
  `MoveAdjacent` is submitted while a preview is active. So `J`/`K` on a dimmed context parent moves its
  group among the displayed top-level rows, like any other top-level row.
  In PR 1 there are no context rows, so `displays` is not added and the
  precheck stays `matches`. `adjacent` still walks the list once; it holds
  one block of lookahead for a top-level row that does not match.
- Reparenting and promotion are ID-based. The new
  `Mutation::SetParent { id, parent: Option<TaskId> }` names both tasks, so
  it needs no adjacency guard. `Mutation::AddSubtask { parent, text }` is the
  other new intent. `Outcome` is unchanged.

```rust
/// The canonical slots of `index`'s root and every subtask after it, tombstones included.
pub fn block(tasks: &[Task], index: usize) -> std::ops::Range<usize> {
    let end = tasks[index + 1..]
        .iter()
        .position(|task| task.parent_id.is_none())
        .map_or(tasks.len(), |offset| index + 1 + offset);
    index..end
}

/// Exchanges two root groups; every slot between them, such as a deleted group, stays put.
pub fn swap_blocks(tasks: &mut [Task], first: usize, second: usize) {
    let (first, second) = if first < second {
        (first, second)
    } else {
        (second, first)
    };
    let (first, second) = (block(tasks, first), block(tasks, second));
    let (first_len, middle_len) = (first.len(), second.start - first.end);
    let span = &mut tasks[first.start..second.end];
    span.rotate_left(first_len); // middle, second, first
    span[..middle_len + second.len()].rotate_left(middle_len); // second, middle, first
}
```

| --- | --- | --- |

| `InvalidParent(ParentError::SelfParent(id))` | `task 5 cannot be its own parent` | `invalid_parent`, the task |
| `InvalidParent(ParentError::ParentIsSubtask(parent))` | `task 4 is a subtask; subtasks cannot have subtasks` | `invalid_parent`, the parent |

### Shell

```text
shtodo [--local] add [--print-id] [--parent <ID>] [<TASK>]
shtodo [--local] parent <ID> <PARENT_ID | none>
shtodo [--local] list [--open | --done] [--tag <TAG>]... [--priority <P>]... [--due <WHEN>]...
              [--search <TEXT>] [--sort priority|due] [--roots | --parent <ID>]
```

**`add`.** `--print-id` and `--parent <ID>` may come in either order
directly after `add`, then the optional text. Each flag is recognized once.
A second occurrence of a flag is the start of the text, so
`add --print-id --print-id` still saves the text `--print-id`, as it does
today. The `--parent` value is the next argument, verbatim, and must be a
positive integer, like task IDs. Text is taken verbatim even if it starts
with `-`. Without text, it is read from stdin as today. `parse_invocation`
skips a `--parent <ID>` pair when it looks for `--json` after `add`, as it
skips `--print-id`, and the trailing `--json` rule (`positional_count` 1 for
`add`) is unchanged. So:

- `add --parent 3 --json` is JSON mode and reads the text from stdin.
- `add --parent 3 --print-id --json` and `add --print-id --parent 3 --json`
  are rejected with `JsonWithPrintId` (`invalid_arguments`, exit 1), as
  `add --print-id --json` is today.
- `add --parent 3 "x" --json` is JSON mode with the text `x`.
- `add --parent --json` is text mode: `--json` is the `--parent` value, so
  it fails with `invalid --parent "--json"; expected a task ID`, like
  `list --tag --json` today.

Success prints `Added: <text>`, or only the ID with `--print-id`, exactly as
today. One compatibility change (question 5): `add --parent` with nothing
after it used to save the text `--parent`, and is now a usage error.

**`parent`.** `parent <ID> <PARENT_ID>` makes ID a subtask of PARENT_ID.
`parent <ID> none` makes ID top-level (`none` is ASCII case-insensitive, like
`--priority none`). `--json` placement follows `edit`, which has the same two
positional arguments: `parse_invocation` gets `"parent" => 2`. So
`--json parent 5 3`, `parent --json 5 3`, and `parent 5 3 --json` are JSON
mode. `parent 5 --json` is not: with only one argument before it, the
trailing `--json` is not popped and becomes PARENT_ID, so it is the
text-mode usage error `invalid parent "--json"; expected a task ID or none`
(exit 1, usage text, no storage created). `edit 1 --json` takes the same
path today but saves the text `--json` and exits 0 (measured on `74747a0`),
because any text is valid there. Text output:

| Case | Output |
| --- | --- |
| Moved under a parent | `5 is now under 3: Write the changelog` |
| Already under that parent | `5 is already under 3: Write the changelog` |
| Promoted | `5 is now top-level: Write the changelog` |
| Already top-level | `5 is already top-level: Write the changelog` |

Moving a subtask from one parent to another is one `parent` call. A no-op
does not save.

**`delete` and `restore` text.** When subtasks move with a parent, the
existing line gains a count: `Deleted 3 with 2 subtasks: Ship the release`
and `Restored 3 with 2 subtasks: Ship the release`. Without subtasks, the
output is byte-identical to today. JSON replies are unchanged in shape
(question 8).

**Text listing.** Rows keep `ID  state  text`. A subtask printed while its
parent's row is the most recent top-level row printed gets two more spaces
before its text:

```text
1  open  Ship the release
2  done    Write the changelog
3  open    Tag the build
4  open  Pay rent due:2026-11-01
```

Stored text never starts with whitespace, so the extra spaces always mean
"subtask under the row above". A subtask whose parent is filtered out prints
like a top-level row, with no indentation. That way it is never drawn inside
an unrelated group. A list with no subtasks prints byte-identical output.
Without `--sort`, output streams in canonical order with O(1) state:

```rust
/// A `list` row; `indented` only when its parent was printed just above its group.
pub struct ListRow<'a> {
    pub task: &'a Task,
    pub indented: bool,
}

/// Streams matching live tasks in canonical order with O(1) state; storage order is the tree.
pub fn list_rows<'a>(
    tasks: impl Iterator<Item = &'a Task>,
    matches: impl Fn(&Task) -> bool,
) -> impl Iterator<Item = ListRow<'a>> {
    let mut printed_root = None;
    tasks.filter_map(move |task| {
        let matched = matches(task);
        match task.parent_id {
            None => {
                printed_root = matched.then_some(task.id);
                matched.then_some(ListRow {
                    task,
                    indented: false,
                })
            }
            Some(parent) => matched.then_some(ListRow {
                task,
                indented: printed_root == Some(parent),
            }),
        }
    })
}
```

The input is `visible_tasks()`. A deleted top-level task is skipped, and so
are its subtasks, which are all tombstones (invariant 3).

**Filters.**

- `--roots` lists top-level tasks only. `--parent <ID>` lists the subtasks
  of ID only, unindented, because ID itself is not printed.
- Each flag may appear at most once, and the two cannot be combined. Both
  combine with every other flag by AND and are checked first, because they
  are the cheapest.
- They live in a new `ListFilter.structure: Structure { Any, Roots,
  Children(TaskId) }`, not in `TaskFilter` or `Projection`. So the TUI and
  `MoveAdjacent` do not change for them.
- An unknown or deleted ID matches nothing: empty output, exit 0
  (question 10).
- `takes_list_value` adds `--parent`, so `list --parent --json` is an
  invalid `--parent` value, like the other value flags.
- Other filters stay exact (question 6). `list --open` shows open tasks only,
  even when their parent is done. A subtask that matches while its parent
  does not is printed unindented, by the rule above.

**Sort.** `--sort priority` and `--sort due` filter first, then sort as a
tree with one helper that both the shell and the TUI cache use:

```rust
/// Sorts rows that are in canonical order as a tree. A group is a root followed by those of
/// its subtasks among the rows; a subtask whose parent is not among the rows is a group of its
/// own. Groups sort by their first row's key and subtasks sort within their group; the sort is
/// stable, so equal keys keep canonical order. Each row's key is computed once.
pub fn sort_tree<K: Clone + Ord>(rows: &mut [&Task], key: impl Fn(&Task) -> K) {
    let mut head: Option<(TaskId, usize, K)> = None;
    let mut keyed = Vec::with_capacity(rows.len());
    for (position, task) in rows.iter().enumerate() {
        let own = key(task);
        let sort_key = match (task.parent_id, &head) {
            (Some(parent), Some((id, group, group_key))) if *id == parent => {
                (group_key.clone(), *group, Some(own))
            }
            _ => {
                head = Some((task.id, position, own.clone()));
                (own, position, None)
            }
        };
        keyed.push((sort_key, position));
    }
    keyed.sort_by(|left, right| left.0.cmp(&right.0));
    let sorted = keyed
        .iter()
        .map(|(_, position)| rows[*position])
        .collect::<Vec<_>>();
    rows.copy_from_slice(&sorted);
}
```

`projection::sort_by_priority` and `sort_by_due` become `sort_tree` with
`priority_key` and `due_key`. On a list with no subtasks, every row is its
own group, so the order is exactly today's. A flat sort that ignores groups
is not offered (question 7). Agents can sort `list --json` themselves.

Orphan rule: sibling subtasks whose parent is filtered out each become their
own group head and sort by their own key. Under `--sort`, unrelated groups
may come between them, and each prints unindented, because its parent was
not printed. For example, subtasks 9 (priority A) and 10 (priority C) of a
filtered-out parent 8, with an unrelated top-level task 11 (priority B),
sort as 9, 11, 10.

### JSON output

Every task object, in `list` and in every mutation reply (deleted tasks
included), gains one always-present field after `due`:

```json
{"id":2,"text":"Write the changelog","state":"done","deleted":false,"priority":null,"tags":[],"due":null,"parent_id":1}
```

| Field | Contract |
| --- | --- |
| `parent_id` | The parent task's scope-local ID as a JSON number, or `null` for a top-level task. Present on deleted tasks too |

- `schema_version` stays `1`. usage.md reserved `parent_id` with exactly this
  shape, and the policy adds always-present nullable fields without a bump.
  usage.md moves `parent_id` from the reserved names to the field table and
  leaves no reserved names.
- No `depth`, `children`, `child_count`, or list of co-deleted IDs
  (question 8). Depth is `parent_id != null`. Children and counts come from
  one pass over the list.
- **Ordering guarantee.** `tasks` is in display order. Without `--sort`,
  that is canonical order, which is tree order. With `--sort`, groups are
  sorted and each group's subtasks are sorted within it. In both cases, when
  a task's parent is in the reply, the parent comes earlier and the parent's
  returned subtasks follow it directly as one run. A task whose `parent_id`
  is not in the reply matched while its parent did not, or its parent was
  excluded by `--parent`. With `--sort`, such
  siblings are sorted as separate heads and need not be adjacent (the orphan
  rule under Sort).

### Performance

Where the tree is built and cached: nowhere as a separate structure. Tree
order is the storage order, guaranteed by validation.

- Validation adds one `Option<&Task>` of state to the existing pass, and no
  allocation.
- Shell `list` streams with one `Option<TaskId>`. `--sort` allocates one
  keyed `Vec`, as today's sorts do.
- `stamp_schema_version` is one scan per save that stops at the first
  subtask. That is about 10,000 boolean checks for a list without subtasks.
- `add --parent` and `parent` do one `Vec` insert or rotation of at most
  10,000 records.
- The TUI builds displayed rows in the same per-frame pass it already makes
  over live tasks. It holds one group of lookahead to decide context rows,
  and counts progress in that pass. The `sorted` cache keeps its rebuild
  points.
- If a TUI gate fails, the first mitigation is per-group counts and
  "has a matching subtask" bits on `App`, rebuilt on reconcile and on
  projection changes. Nothing is cached in `TaskList` or storage.
- JSON adds `,"parent_id":null`, 17 bytes per task: about 170,000 bytes at
  10,000 tasks, against 1,128,968 bytes for the plain fixture today. The due
  field added 110,000 bytes and cost 0.28 to 0.76 ms, so expect about 0.4 to
  1.0 ms. That is inside the absolute bound, and possibly over 10% on the
  smallest fixture.

## STOP conditions

Stop and report to the owner instead of continuing when:

- The owner has not accepted question 1. No stored field or schema change
  lands without it.
- A list without subtasks would be written as anything but schema 1 bytes
  identical to today's, or any older binary could write to a schema 2 list.
- Any invariant can be violated by a mutation that passes its checks, or a
  validation failure would leave a partially written snapshot.
- A JSON change would alter or remove an existing v1 field, or an existing
  command would return a new error code.
- A PR 1 or PR 2 gate fails by both its relative and absolute bounds after
  the listed mitigations, or idle refresh starts parsing or redrawing
  unchanged bytes.
- Tree order cannot be kept with ID-based intents and the existing
  `MoveAdjacent` contract.
- A new default key breaks loading of any existing valid config or needs a
  new reserved key, or Help under the Stage 3a layout cannot show every row
  at 80x24, with default keys or the long-alias test keymap, without
  scrolling (question 16).
- An existing command other than `restore` would return `task_deleted` with
  a `task_id` other than the ID it was given.
- Indentation or progress would hide the status marker at 40 columns, or
  the hint and list rows would fall below the 40x8 minimums from the earlier
  plans.
- A dependency would be added.
- The owner asks for deeper nesting, collapse, cascade completion, purge,
  notifications, reminders, recurrence, or times in this slice; replan
  rather than grow scope.
- Work would touch CI, workflows, secrets, releases, or files outside this
  worktree, or would need a push or PR without explicit authorization.

## Open questions for the owner

1. **Stored link and compatibility.** Store `parent_id` on the task record
   and write schema 2 only while a list has at least one subtask (schema 1
   otherwise, byte-identical)? Older binaries, from beta.1 to beta.4 and the
   unreleased tags and due-dates builds, then refuse such a list with
   `unsupported schema version 2` and never write it. This relaxes the
   earlier "old and new binaries share files both ways" guarantee to "until
   a list has its first subtask", per list. New binaries read schema 1 and
   schema 2, and accept a schema 2 file that has no `parent_id`; the next
   real save writes it as schema 1. Default: accept. The only no-schema
   alternative is a text token, rejected under Alternatives.
2. **Depth.** One level of subtasks? Default: yes. Deeper nesting later
   would use schema 3 under the same lowest-version rule.
3. **Deleting a parent.** Move its live subtasks to trash with it under one
   deletion sequence, restore exactly those with it, and refuse restoring a
   subtask while its parent is in trash? Default: yes.
4. **Completion.** No cascade in either direction? Default: yes. The
   alternative, refusing to complete a parent with open subtasks, adds an
   error to an existing command.
5. **Shell commands.** `add --parent <ID>` to create and
   `parent <ID> <PARENT_ID|none>` to reparent or promote? Default: yes. Other
   names considered: `move --under`, `nest`/`unnest`. One existing behavior
   changes: `add --parent` with nothing after it saves the text `--parent`
   today and becomes a usage error. `add --parent foo` is already rejected
   today (two text arguments, measured on `74747a0`); only its message
   changes, to `invalid --parent "foo"; expected a task ID`.
6. **Filtered shell output.** Exact matches only, the same set in text and
   JSON, with a subtask whose parent is filtered out printed unindented?
   Default: yes. The TUI alone shows dimmed context parents.
7. **Sort.** Sort as a tree (groups by their top-level row, subtasks within
   their group)? Default: yes; no flat sort flag.
8. **Extra JSON.** Add `depth`, `children`, `child_count`, or the IDs of
   subtasks deleted with a parent? Default: none of them; `parent_id` plus
   the ordering guarantee is enough.
9. **Error codes.** One new code, `invalid_parent`, produced only by
   `add --parent` and `parent`; a parent in trash reuses `task_deleted` with
   `task_id` naming the parent? Default: yes. This gives `restore` its first
   `task_deleted` reply, with a `task_id` that differs from the requested
   ID; usage.md and the skill say so, and agents restore `error.task_id`
   first. The alternative is a second new code, `parent_deleted`, which
   `restore` (an existing command) would then return.
10. **`list --parent` with an unknown or deleted ID.** Empty success, like
    any filter that matches nothing? Default: yes. The alternative is
    `task_not_found`.
11. **Nesting a task whose only subtasks are in trash.** Allow it, turning
    those deleted subtasks into top-level tasks in trash? Default: yes.
    Refusing would leave the task impossible to nest, because nothing can
    be purged.
12. **TUI keys.** `A` add subtask, `>` nest under the task above, `<`
    promote, all yielding to existing bindings? Default: yes. `a` is avoided
    because the documented example config binds it to `add_task`.
13. **Collapse and expand.** Defer to a later TUI-only change? Default:
    defer.
14. **Parent progress and context rows.** Show a dim `done/total` after a
    parent's marker, and dimmed context parents above matching subtasks in
    the TUI? Default: yes to both.
15. **Binary size bound.** 2% or 32 KiB on `aarch64-apple-darwin` for each
    PR, since no dependency is added? Default: yes. Linux musl is reported
    only.
16. **Help layout at 80x24.** Help has no spare row today: one more Normal
    row already breaks the long-alias Help test. Let the Help popup cover the
    header row (its top border carries the header text, and the open and
    done counts are hidden while Help is open), drop its bottom border so
    the footer stays, and show `>` and `<` on one row? That gives 22 inner
    rows: 21 used with default keys after Stage 3c and 22 with the
    long-alias test keymap. Two things to weigh: (a) the shared row is a

    - (A) Default: yes, and the next Normal action must add Help scrolling.
