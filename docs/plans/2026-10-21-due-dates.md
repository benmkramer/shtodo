## Recommendation

Keep the due date inside the task text as a todo.txt `due:YYYY-MM-DD` token and
derive it on demand, exactly as priority and tags are derived. A token is a
whitespace-delimited word anywhere in the text that starts with the lowercase
key `due:` followed by a real calendar date in `YYYY-MM-DD` form, after
trailing `.,;:!?` is stripped. The first valid token is the task's due date.
Anything else, including `due:2026-02-30` and `due:soon`, is plain text. Do not
add stored fields, change on-disk schema 1, or migrate beta.4 data; old and new
binaries keep sharing the same `tasks.json`. A future todo.txt export writes
the text unchanged.

Accept `due:today` and `due:tomorrow` on input and rewrite them to dates when
a task is added or edited, in the shell and in the TUI. Stored text then
always holds an absolute date, so its meaning never drifts and every reader
in any time zone agrees on it. Relative words are never resolved at read time.
"Today" is the local calendar date of the running process, read through one
small `clock` module. Every other function takes a `Date` (or a closure that
returns one), so tests inject a fixed date and the storage layer, mutations,
and `TaskList` never read the clock. Reading the local date needs one new
dependency; the default is `jiff` 0.2 with minimal features, whose embedded
zone database is compiled only on Windows, plus a small zone-name lookup in
`clock.rs` on Unix that keeps the first clock read under half a millisecond
(open questions 1, 13, and 14). Its
binary size is checked first, in Stage 1, with a fallback ladder before any
STOP.

Shell `list` gains a repeatable `--due` filter (`today`, `tomorrow`,
`overdue`, `none`, `any`, a date, or a range such as `2026-10-01..2026-10-31`)
and `--sort due`, which orders by date with priority breaking ties. Both
compose with every existing flag and are honored identically by `--json`.
JSON task objects gain the reserved, always-present `due` field (a
`"YYYY-MM-DD"` string or `null`); `schema_version` stays `1` under the
additive policy. In the TUI, the due token is styled in place, the row's
status marker turns red when an open task is overdue and yellow when it is due
today (the marker is always visible at 40 columns), `s` cycles Manual,
Priority, and Due order with no new binding, and the `f` filter editor accepts
`due:` tokens with the existing preview and Enter rules. The TUI checks the
date at each one-second refresh deadline, and at its own one-second deadline
while successful writes postpone the refresh, and redraws only when the date
changes.

Ship it as two PRs, like the previous plan. PR 1 (shell, JSON, and add/edit
normalization in both interfaces) is useful to agents on its own; PR 2 adds
TUI styling, Due order, and due filter tokens.

## Alternatives

### Storing the due date

| Approach | Benefits | Costs and failure modes | Decision |
| --- | --- | --- | --- |
| Token stays in text; derive on demand | No schema change or migration; beta.4, the tags release, and new binaries share files both ways; todo.txt export is free; one source of truth | Text that happens to contain `due:2026-01-01` becomes a due date; every reader that needs the date scans text; changing a date is a text edit | Recommend |
| Token in text plus an in-memory parse cache filled at load (`#[serde(skip)]`) | One parse per task per load | Pays the parse on every load and refresh even when nothing uses dates; cache consistency code in `add`/`edit` | Reject; the TUI caches only its sorted order (see Performance) |
| Stored `due` field, token stripped from text | Structured edits, no accidental dates | Schema 2 and a migration; `deny_unknown_fields` makes every released binary fail on new files and stops an open older TUI from refreshing; export must reassemble text | Reject |
| Stored field and the token kept in text | Fast structured reads | Same compatibility break, plus the two can disagree | Reject |

## Contracts

### Token grammar

All parsing is on canonical (validated, trimmed) task text.

- **Due token**: a whitespace-delimited token (Unicode whitespace, as for tags)
  that starts with the exact lowercase key `due:`, anywhere in the text. After
  trailing ASCII `.`, `,`, `;`, `:`, `!`, and `?` are stripped, the rest must
  be exactly ten bytes `YYYY-MM-DD` of ASCII digits naming a real proleptic
  Gregorian day: month `01` to `12`, day `01` to the month's length, with leap
  years. Years `0000` to `9999` are accepted.
- The task's due date is the first valid due token in text order. Later due
  tokens, valid or not, stay plain text and are ignored. Input rewriting is
  different: it rewrites every relative token (see Relative words on input),
  so `x due:today due:tomorrow` is saved as `x due:2026-10-21 due:2026-10-22`
  and is due 2026-10-21.
- **Invalid, and therefore plain text**: `due:` alone; `due: 2026-11-01` (a
  space); `Due:` or `DUE:`; `overdue:2026-11-01` and `+due:2026-11-01` (the key
  is not at the token start); `due:2026-1-5`; `due:26-10-21`;
  `due:2026/10/21`; `due:2026-02-30`; `due:2026-13-01`; non-ASCII digits;
  `due:2026-11-01T09:00` and `due:2026-11-01)` (extra characters after
  stripping); and a stored relative word such as `due:today`, which only an
  older binary or a direct file edit can store.
- A due token is never a tag (it has no sigil) and never a priority, so all
  three can appear in one text: `(A) Pay rent due:2026-11-01. +home`.
- Completion is still the `completed` field. Completing a task keeps its due
  token, and a done task is never overdue.
- Search (`/` and `--search`) still matches the full literal text, so
  `/due:2026-11` finds those tokens as text.

Proposed additions to `src/metadata.rs` (pure functions on `&str`; `due_token`
allocates nothing):

```rust
/// A proleptic Gregorian calendar date; field order makes the derived `Ord` chronological.
#[derive(Clone, Copy, Debug, Eq, Hash, Ord, PartialEq, PartialOrd)]
pub(crate) struct Date {
    year: u16,
    month: u8,
    day: u8,
}

impl Date {
    pub(crate) const MIN: Self = Self {
        year: 0,
        month: 1,
        day: 1,
    };
    pub(crate) const MAX: Self = Self {
        year: 9999,
        month: 12,
        day: 31,
    };

    pub(crate) fn new(year: u16, month: u8, day: u8) -> Option<Self> {
        (year <= 9999
            && (1..=12).contains(&month)
            && (1..=days_in_month(year, month)).contains(&day))
        .then_some(Self { year, month, day })
    }

    /// Exactly `YYYY-MM-DD` in ASCII digits, and a real calendar day.
    pub(crate) fn parse(text: &str) -> Option<Self> {
        let &[y0, y1, y2, y3, b'-', m0, m1, b'-', d0, d1] = text.as_bytes() else {
            return None;
        };
        let digit = |byte: u8| byte.is_ascii_digit().then(|| u16::from(byte - b'0'));
        let year = digit(y0)? * 1000 + digit(y1)? * 100 + digit(y2)? * 10 + digit(y3)?;
        let month = digit(m0)? * 10 + digit(m1)?;
        let day = digit(d0)? * 10 + digit(d1)?;
        Self::new(year, u8::try_from(month).ok()?, u8::try_from(day).ok()?)
    }

    pub(crate) fn succ(self) -> Option<Self> {
        Self::new(self.year, self.month, self.day + 1)
            .or_else(|| Self::new(self.year, self.month + 1, 1))
            .or_else(|| Self::new(self.year.checked_add(1)?, 1, 1))
    }

    pub(crate) fn pred(self) -> Option<Self> {
        if self.day > 1 {
            return Some(Self {
                day: self.day - 1,
                ..self
            });
        }
        let (year, month) = match self.month {
            1 => (self.year.checked_sub(1)?, 12),
            month => (self.year, month - 1),
        };
        Self::new(year, month, days_in_month(year, month))
    }
}

impl fmt::Display for Date {
    fn fmt(&self, formatter: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(
            formatter,
            "{:04}-{:02}-{:02}",
            self.year, self.month, self.day
        )
    }
}

fn days_in_month(year: u16, month: u8) -> u8 {
    match month {
        2 if year % 4 == 0 && (year % 100 != 0 || year % 400 == 0) => 29,
        2 => 28,
        4 | 6 | 9 | 11 => 30,
        _ => 31,
    }
}

const DUE_KEY: &str = "due:";

/// The first valid due token as its `due:YYYY-MM-DD` slice (for row styling) and its date.
pub(crate) fn due_token(text: &str) -> Option<(&str, Date)> {
    // Most texts have no key; `contains` is the cheapest rejection, and searching for the key
    // avoids splitting the whole text on Unicode whitespace.
    if !text.contains(DUE_KEY) {
        return None;
    }
    text.match_indices(DUE_KEY).find_map(|(start, _)| {
        let token_start = text[..start]
            .chars()
            .next_back()
            .is_none_or(char::is_whitespace);
        if !token_start {
            return None;
        }
        let token = text[start..].split(char::is_whitespace).next()?;
        let value = token[DUE_KEY.len()..].trim_end_matches(TRAILING_PUNCTUATION);
        let date = Date::parse(value)?;
        Some((&token[..DUE_KEY.len() + value.len()], date))
    })
}

pub(crate) fn due(text: &str) -> Option<Date> {
    due_token(text).map(|(_, date)| date)
}
```

The returned slice borrows the text and excludes stripped punctuation, so row
styling highlights exactly `due:2026-11-01` in `Pay due:2026-11-01.`, as
`text_spans` already does for tags.

### Relative words on input

- At add and edit time only, every due token whose value (after stripping
  trailing `.,;:!?`) is `today` or `tomorrow`, ASCII case-insensitive, has
  that word replaced by the date. The key stays lowercase-only: `Due:today`
  is plain text and is not rewritten. Everything else in the text, including
  the stripped punctuation and other due tokens, keeps its exact bytes:
    `(A) Pay due:Today. +home` becomes `(A) Pay due:2026-10-21. +home`.
- Every relative due token is rewritten, not only the first, while only the
  first valid token is the due date: `x due:today due:tomorrow` is saved as
  `x due:2026-10-21 due:2026-10-22`, whose due date is 2026-10-21. Rewriting
  all of them keeps stored text free of relative words, so no token can
  change meaning on a later day.
- `today` is the local date at the moment the command runs (shell) or the
  date the TUI is displaying when Enter is pressed (see Clock). `tomorrow` is
  the next calendar day. If the next day does not exist (`9999-12-31`), the
  word is left unchanged and stays plain text.
- Weekday names (`due:fri`), offsets (`due:+3d`), and `week` are not accepted
  on input in this slice; they stay plain text (open question 2). They can be
  added later without changing stored data, because stored text only ever
  holds absolute dates.
- The rewrite runs before `validated_text`'s unchanged comparison, so
  `edit 3 "Pay due:today"` on a task whose text is already
  `Pay due:2026-10-21` reports `Unchanged` and writes nothing, in both text
  and JSON mode.
- The clock is read at most once per add or edit, and only when a relative
  word is present; plain text never touches the clock.
- Callers: `lib::add_task` before `Mutation::Add`, the shell `edit` path
  before `TaskMutation::Edit`, and `App::commit_edit` before it builds
  `Mutation::Add` or `Mutation::EditText`. `Mutation`, `storage`, and
  `TaskList` stay clock-free.
- An older binary does not rewrite relative words. If it stores
  `due:today`, newer binaries treat that token as plain text forever, never
  as a moving date. usage.md says so.

```rust
/// Rewrites `due:today` and `due:tomorrow` (ASCII case-insensitive words) to dates at add and
/// edit time. `today` is called at most once, and only when such a word is present.
pub(crate) fn normalize_due(text: &str, mut today: impl FnMut() -> Date) -> Cow<'_, str> {
    if !text.contains(DUE_KEY) {
        return Cow::Borrowed(text);
    }
    let mut resolved = None;
    let mut normalized = String::new();
    let mut copied = 0;
    for token in text.split_whitespace() {
        let Some(value) = token.strip_prefix(DUE_KEY) else {
            continue;
        };
        let word = value.trim_end_matches(TRAILING_PUNCTUATION);
        let date = if word.eq_ignore_ascii_case("today") {
            Some(*resolved.get_or_insert_with(&mut today))
        } else if word.eq_ignore_ascii_case("tomorrow") {
            resolved.get_or_insert_with(&mut today).succ()
        } else {
            None
        };
        let Some(date) = date else {
            continue;
        };
        // Tokens borrow `text`, so the word's offset comes from the slice addresses.
        let start = word.as_ptr().addr() - text.as_ptr().addr();
        normalized.push_str(&text[copied..start]);
        normalized.push_str(&date.to_string());
        copied = start + word.len();
    }
    if copied == 0 {
        return Cow::Borrowed(text);
    }
    normalized.push_str(&text[copied..]);
    Cow::Owned(normalized)
}
```

### Clock

- New module `src/clock.rs` with one function,
  `pub(crate) fn today() -> metadata::Date`: the calendar date in the
  process's local time zone. It is the only code that reads the system clock
  or zone. It converts `SystemTime::now()` with `jiff::Timestamp::try_from`
  (not `Timestamp::now()`, which panics outside jiff's range), takes the civil
  date in the zone resolved below, and maps the year, month, and day through
  `Date::new`, so `today()` has no panic path. A clock past jiff's last
  timestamp (9999-12-30T22:00:00Z) clamps to `Date::MAX`. A clock before
  jiff's first timestamp, or one that gives a negative year (before 1 BCE),
  clamps to `Date::MIN`. No real clock reaches either clamp; the unit test
  `clocks_outside_the_civil_range_should_clamp_to_the_nearest_end` covers
  both through `today_at(now, zone)`.
- Dependency, the same line on every platform (checked against jiff 0.2.38):

  ```toml
  jiff = { version = "0.2.38", default-features = false, features = ["std", "tz-system", "tzdb-bundle-platform"] }
  ```

  `tzdb-zoneinfo`, `tz-fat`, `perf-inline`, and `tzdb-concatenated` are off.
  Without `tzdb-zoneinfo`, jiff cannot resolve an IANA name on Unix, so
  `clock.rs` resolves names itself (below). That avoids the zoneinfo
  database setup that made the first read 0.7 to 1.0 ms (open question 13,
  whose default flipped in review cycle 2). `tzdb-bundle-platform` depends on
  `jiff-tzdb-platform` only under `cfg(any(windows, target_family = "wasm"))`,
  so on macOS and Linux it compiles nothing. On Windows, which has no system
  copy of the database, it embeds `jiff-tzdb` (0.1.9), and `tz-system` adds
  `windows-link`. This design keeps the bundle for Windows (open question 14).
- Zone resolution, in this order, cached for the life of the process in a
  `OnceLock<TimeZone>`. Nothing outside a running process can change its
  `TZ`, and the C library likewise loads the zone once.
  1. Unix, `TZ` unset: read `/etc/localtime`, following symlinks, and pass the
     bytes to `jiff::tz::TimeZone::tzif`. jiff's own system lookup also
     handles this case (the probe found the right date with no database), but
     its documentation says only that a symlink's suffix "is considered an
     IANA Time Zone Database identifier" and does not state a fallback without
     a database. So `clock.rs` does not rely on it. If the file is missing or
     is not TZif, go to step 4.
  2. Unix, `TZ` set: strip one leading `:` (the implementation-defined POSIX
     form, which glibc and macOS accept). If the rest is valid UTF-8,
     non-empty, not absolute, and has no empty or `..` component, read
     `$TZDIR/<name>` when `TZDIR` is set and non-empty, and otherwise
     `/usr/share/zoneinfo/<name>`. Pass the bytes to `TimeZone::tzif`. On macOS
     `/usr/share/zoneinfo` is a symlink to `/var/db/timezone/zoneinfo`, which
     `fs::read` follows. The lookup is case-sensitive on case-sensitive file
     systems, as the C library's is. If the file is missing or is not TZif, go
     to step 4, so a POSIX string such as `UTC0` (not a file) reaches jiff.
  3. Windows: no file lookup; go to step 4.
  4. `jiff::tz::TimeZone::system()`. Its documented behavior covers every
     remaining form: `TZ` as an absolute TZif path (the probe also verified
     the `:`-prefixed path); a POSIX rule string; and on Windows, an IANA name
     from the embedded database, or with `TZ` unset, the system zone through
     `GetDynamicTimeZoneInformation` and CLDR data. An empty, invalid, or
     unresolvable value gives jiff's unknown zone, which "behaves like
     `TimeZone::UTC`".

  | Platform | `TZ` unset | `TZ` an IANA name (`America/New_York`, `:America/New_York`) | `TZ` an absolute path | `TZ` a POSIX string (`<-12>12`) | `TZ` empty, invalid, or a missing name |
  | --- | --- | --- | --- | --- | --- |
  | macOS, Linux | `/etc/localtime`, read by `clock.rs` | `$TZDIR` or `/usr/share/zoneinfo`, read by `clock.rs` | jiff reads the file | jiff parses it | UTC date |
  | Linux without tzdata (minimal containers) | UTC date | UTC date | jiff reads the file if it exists | jiff parses it | UTC date |
  | Windows | jiff: `GetDynamicTimeZoneInformation`, CLDR mapping, embedded database | jiff: embedded database | jiff reads the file | jiff parses it | UTC date |

### Filter model shared by shell and TUI

Add to `src/metadata.rs`:

```rust
/// One `--due` value, or the value of a `due:` filter-editor token, before `today` is known.
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub(crate) enum DueTerm {
    /// No valid due token.
    None,
    /// Any valid due token.
    Any,
    /// Open, and due before today.
    Overdue,
    /// Due within the inclusive range; an omitted bound is unbounded.
    Range {
        start: Option<DueBound>,
        end: Option<DueBound>,
    },
}

#[derive(Clone, Copy, Debug, Eq, PartialEq)]
pub(crate) enum DueBound {
    Today,
    Tomorrow,
    Date(Date),
}

impl DueBound {
    fn parse(value: &str) -> Option<Self> {
        if value.eq_ignore_ascii_case("today") {
            Some(Self::Today)
        } else if value.eq_ignore_ascii_case("tomorrow") {
            Some(Self::Tomorrow)
        } else {
            Date::parse(value).map(Self::Date)
        }
    }

    fn resolve(self, today: Date) -> Option<Date> {
        match self {
            Self::Today => Some(today),
            Self::Tomorrow => today.succ(),
            Self::Date(date) => Some(date),
        }
    }

    /// Ordered without knowing today, when both bounds are absolute or both relative.
    fn known_after(self, other: Self) -> bool {
        match (self, other) {
            (Self::Date(start), Self::Date(end)) => start > end,
            (Self::Tomorrow, Self::Today) => true,
            _ => false,
        }
    }
}

pub(crate) fn parse_due_term(value: &str) -> Option<DueTerm> {
    for (word, term) in [
        ("none", DueTerm::None),
        ("any", DueTerm::Any),
        ("overdue", DueTerm::Overdue),
    ] {
        if value.eq_ignore_ascii_case(word) {
            return Some(term);
        }
    }
    let Some((start, end)) = value.split_once("..") else {
        let bound = DueBound::parse(value)?;
        return Some(DueTerm::Range {
            start: Some(bound),
            end: Some(bound),
        });
    };
    let bound = |value: &str| match value {
        "" => Some(None),
        value => DueBound::parse(value).map(Some),
    };
    let (start, end) = (bound(start)?, bound(end)?);
    match (start, end) {
        (None, None) => None,
        (Some(start), Some(end)) if start.known_after(end) => None,
        _ => Some(DueTerm::Range { start, end }),
    }
}

/// A resolved inclusive span; `start > end` is empty.
#[derive(Clone, Copy, Debug, Eq, PartialEq)]
struct DueSpan {
    start: Date,
    end: Date,
    open_only: bool,
}

/// `--due` terms, a union; empty means any. Terms stay unresolved so a new day only re-resolves.
#[derive(Clone, Debug, Default, Eq, PartialEq)]
pub(crate) struct DueFilter {
    terms: Vec<DueTerm>,
    /// Spans for `terms` on one local date. Unresolved terms match nothing (fail closed).
    spans: Option<Vec<DueSpan>>,
}

impl DueFilter {
    pub(crate) fn is_empty(&self) -> bool {
        self.terms.is_empty()
    }

    pub(crate) fn add(&mut self, term: DueTerm) {
        if !self.terms.contains(&term) {
            self.terms.push(term);
        }
        self.spans = None;
    }

    /// Calls `today` only when a term depends on it, so absolute filters never read the clock.
    pub(crate) fn resolve(&mut self, today: impl FnOnce() -> Date) {
        let relative = |bound: Option<DueBound>| !matches!(bound, None | Some(DueBound::Date(_)));
        let today = self
            .terms
            .iter()
            .any(|term| match *term {
                DueTerm::Overdue => true,
                DueTerm::Range { start, end } => relative(start) || relative(end),
                DueTerm::None | DueTerm::Any => false,
            })
            .then(today);
        let at = |bound: Option<DueBound>, unbounded| match (bound, today) {
            (None, _) => Some(unbounded),
            (Some(DueBound::Date(date)), _) => Some(date),
            (Some(bound), Some(today)) => bound.resolve(today),
            (Some(_), None) => None,
        };
        // A bound that does not exist (the day before 0000-01-01) makes the span empty.
        let span = |start: Option<Date>, end: Option<Date>, open_only| match (start, end) {
            (Some(start), Some(end)) => DueSpan {
                start,
                end,
                open_only,
            },
            _ => DueSpan {
                start: Date::MAX,
                end: Date::MIN,
                open_only,
            },
        };
        let spans = self.terms.iter().filter_map(|term| match *term {
            DueTerm::None => None,
            DueTerm::Any => Some(span(Some(Date::MIN), Some(Date::MAX), false)),
            DueTerm::Overdue => Some(span(Some(Date::MIN), today.and_then(Date::pred), true)),
            DueTerm::Range { start, end } => {
                Some(span(at(start, Date::MIN), at(end, Date::MAX), false))
            }
        });
        self.spans = Some(spans.collect());
    }

    pub(crate) fn matches(&self, due: Option<Date>, completed: bool) -> bool {
        if self.is_empty() {
            return true;
        }
        let Some(spans) = &self.spans else {
            return false;
        };
        match due {
            None => self.terms.contains(&DueTerm::None),
            Some(date) => spans.iter().any(|span| {
                !(span.open_only && completed) && span.start <= date && date <= span.end
            }),
        }
    }
}
```

### Shell `list`

```text
shtodo [--local] list [--open | --done] [--tag <TAG>]... [--priority <P>]... [--due <WHEN>]... [--search <TEXT>] [--sort priority|due] [--json]
```

- `--due <WHEN>` repeats as a union. `WHEN` is one of:

  | Value | Matches |
  | --- | --- |
  | `today`, `tomorrow` | Tasks due on that local date |
  | `overdue` | Open tasks due before today; never done tasks |
  | `YYYY-MM-DD` | Tasks due on that date |
  | `START..END` | Tasks due from START to END inclusive; each bound is a date, `today`, or `tomorrow`; one bound may be omitted (`..2026-10-31`, `today..`) |
  | `none` | Tasks without a valid due token |
  | `any` | Tasks with a valid due token |

  Words are ASCII case-insensitive (`TODAY`, `None`), matching `--priority`'s
  `none`. A `week` value is out of scope (open question 5): its start day is
  locale-dependent, and `--due today..2026-10-28` says exactly what is meant.
- Composition: filter first, then sort. `--open --due overdue` equals
  `--due overdue`; `--done --due overdue` is always empty;
  `--done --due ..2026-10-20` lists done tasks that were due by then. `--due`
  combines with `--tag`, `--priority`, and `--search` with AND.
- `--sort` still takes exactly one value, now `priority` or `due`, and appears
  at most once. `--sort due` orders by due date, earliest first, then tasks
  without a due date; equal dates are ordered by priority (`A` to `Z`, then
  none), then saved order. `--sort priority` is unchanged (ties keep saved
  order). Composite keys such as `--sort due,priority` are not added (open
  question 6). Text rows and JSON objects are unchanged; only their order
  differs.
- Each flag value is the next argument verbatim, so `list --due --json` is an
  invalid `--due` value; put `--json` before `list`.
- A filter that matches nothing is success: empty stdout or `"tasks":[]`,
  exit 0. Every argument error is detected before storage or the clock is
  read. Reads stay side-effect free.

```rust
/// Display order for a projection. Storage and reorder guards never need it.
#[derive(Clone, Copy, Debug, Default, Eq, PartialEq)]
pub(crate) enum TaskOrder {
    #[default]
    Manual,
    Priority,
    Due,
}

/// Priority order's sort key: `A` to `Z`, then no priority.
pub(crate) fn priority_key(task: &Task) -> (bool, Option<metadata::Priority>) {
    let priority = metadata::priority(task.text());
    (priority.is_none(), priority)
}

type DueKey = (
    bool,
    Option<metadata::Date>,
    (bool, Option<metadata::Priority>),
);

/// Due order's sort key: earliest date first, then no due date; priority breaks date ties.
pub(crate) fn due_key(task: &Task) -> DueKey {
    let due = metadata::due(task.text());
    (due.is_none(), due, priority_key(task))
}

/// Stable, and parses each task once: equal keys keep canonical order.
pub(crate) fn sort_by_due(tasks: &mut [&Task]) {
    tasks.sort_by_cached_key(|task| due_key(task));
}
```

### Performance

- Plain text `list` without `--due` or `--sort due` does no due work and no
  clock read.
- `list --json` pays one `due` parse per task: a `contains("due:")` rejection
  for most texts (about 4 ns) and a key search plus a ten-byte parse for
  dated texts (about 45 ns), from the planning micro-measurement.
- Shell filters check cheapest first: tombstone, view, priority, due (only if
  requested), tags (only if requested), then search. `--sort due` collects
  the filtered rows and parses each once (`sort_by_cached_key`).
- No load-time cache, no stored field, so storage parsing and refresh costs
  stay the same.
- Where parsing is cached: the TUI's existing `sorted` index cache holds Due
  order, built with one parse per live task on `reconcile` and order changes
  only. Row styling parses only the visible window per frame. A due filter
  parses each live task's text per keystroke or reconcile while it is active.
  If the TUI filter gate fails, the first mitigation is a per-canonical-index
  `Vec<Option<Date>>` on `App`, rebuilt beside `sorted` on `reconcile`;
  nothing is cached in `TaskList` or storage.
- Idle: one local-date read per refresh deadline (the date deadline coincides
  with it); no parse and no redraw
  unless the bytes or the date change.

## STOP conditions

Stop and report to the owner instead of continuing when:

- Any design needs a stored field, an on-disk `schema_version` change, or a
  migration, or makes beta.4 or the tags release unable to read a snapshot
  this branch wrote.
- A JSON change would alter or remove an existing v1 field.
- The owner has not approved the date dependency; or the size gate still
  fails after the ladder under Clock (trim features, then `libc` if
  pre-approved), in which case the report gives each rung's measured size on
  each platform; or `unsafe` code would be needed beyond the one pre-approved
  `localtime_r` call; or `clock::today()` could return an error.
- A clock-dependent integration test can neither run on Windows nor be
  `#[cfg(unix)]`-gated with a recorded reason.
- Anything outside `clock.rs` needs to read the system clock or zone, or the
  storage layer, `Mutation`, or `TaskList` would need a date.
- A relative word would need to be resolved at read time.
- A PR 1 or PR 2 gate fails by both its relative and absolute bounds after
  the listed mitigations, or idle refresh starts parsing or redrawing
  unchanged bytes on an unchanged date.
- A key change would break loading of any existing valid config, or would
  need a new reserved key.
- Reorder under a due filter cannot be guarded with the existing
  `MoveAdjacent` contract.
- Due filter state leaks a prefix or preview into `TaskFilter`, `Projection`,
  or a `Mutation`.
- The status marker cannot carry overdue and due-today state at 40 columns
  without changing row width.
- The owner asks for times, reminders, notifications, recurrence, or subtasks
  in this slice; replan rather than grow scope.
- Work would touch CI, workflows, secrets, releases, or files outside this
  worktree, or would need a push or PR without explicit authorization.
  Dependency changes are limited to the one approved in question 1.
